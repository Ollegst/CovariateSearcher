## Cross-cutting hazards & consolidation candidates (read before any merge)

**Duplicate implementations (merge targets — but preserve contracts):**
- **Control-stream / listing readers ×1 (consolidated 2026-10-26, G13):** every `.ctl`/`.mod` read goes through `.read_control_stream()` and every `.lst` read through `.read_listing_lines()`, both repairing non-UTF-8 lines as CP1252 (`.repair_encoding`). A new bare `readLines()` on a control stream reintroduces NIO-01 (a cp1252 comment line silently counted as a THETA). `.ext`/`.cov`/`.cor`/YAML reads are numeric or ASCII and stay on `readLines`.
- **`.ext` readers ×3:** `read_nonmem_ext` (file-io.R → `found/ofv/parameters`, FINAL `-1e9` line, flat+subdir), `read_ext_file` (monitoring-files.R → `status/current_ofv/iterations/has_estimation_issues/…`, last/current line, subdir-only), `read_ext_iterations` (plot_nonmem_iterations.R → tidy data.frame, consumed positionally by the sim sampler). **Different OFV semantics + file locations — do not conflate.**
- **`.cov`/`.cor` matrix parsers ×2:** `calculate_condition_number` (model-output-tables.R, reconstructs lower-triangular) vs `.read_nonmem_matrix` (forest-plots.R, assumes labelled square).
- **`$THETA` numbering ×1 (consolidated 2026-10-26, G1):** THETA numbers come only from `.parse_theta_records()` (file-io.R) — one row per value, several per line counted. Used by `model_add_cov` (next number), `remove_covariate_from_model` (Step 4), `validate_parameter_blocks` (one value per line, via `.count_theta_values`), `apply_covariate_model` and `.structural_param_names` (names). A new hand-rolled line counter reintroduces MOD-01/MOD-12.
- **`require_cov_step` ×1 (consolidated 2026-10-26, G5):** read only through `.require_cov_step()` (explicit FALSE relaxes, anything else is TRUE) and checked at the entry points by `.check_require_cov_step()`. A new `search_config$require_cov_step %||% TRUE` read with `isTRUE()` or `if (x)` reintroduces XAR-05 (NA meant three different things).
- **`$THETA` name/trans parsers (still separate):** `extract_params`/`extract_model_params` (model-output-tables.R, one row per line — fine because validation now rejects multi-value lines) and inline in `create_covariate_table`. The two inline copies in `apply_covariate_model` / `.structural_param_names` were replaced by the parser on 2026-10-26. `.name_scale_inputs` (plot-bootstrap-distributions.R) looks like a fourth but is not: it derives the same LOG/diagonal *branches* from the parameter **name** plus the `log_cols` list `.listing_column_meta()` already produced, and never opens a control stream. A bootstrap draw arrives as a bare name and a number, which is the only reason it exists; anything it needs from `$THETA` must keep coming through `.listing_column_meta` → `extract_model_params`.
- **Reported-scale mapping ×1 (consolidated 2026-08-23 — do not re-derive):** "`;LOG` theta → `exp()`, OMEGA/SIGMA diagonal → CV%" now lives only in `.to_report_scale()` (model-output-tables.R). `get_param2()`'s `Parameter` column, both bounds of its asymptotic `95% CI`, and both the draws and the final estimate in `plot_bootstrap_distributions()` all pass through it, so a table cell, an interval and a histogram panel cannot end up on different scales. The mapping is monotone increasing in every branch, which is what makes mapping a CI's bounds independently legitimate. **One deliberate exception:** `get_param2`'s `RSE` `case_when` repeats the same four branch conditions with different arithmetic and was not folded in — a new case in the scale mapping needs its RSE counterpart added by hand.
- **Categorical-level decode ×2+:** `decode_cov_level` (model-output-tables.R, the only unit-tested fn) vs nested `decode_level` (forest-plots.R) vs the inline decode in `model_add_cov`.
- **Covariate formula algebra ×2 (highest risk):** `model_add_cov` *writes* NONMEM factors; `apply_covariate_model` *reconstructs the same math in R*. Must stay in sync. Also, `model_add_cov`'s formula block is **duplicated verbatim within itself** (~L404-408 and ~L490-494).
- **name→tag idiom** `names(tags)[tags==name]` repeated ~6× in scm-selective-forward.R + full_scm_search.R; overlaps `get_covariate_tag_from_name`.
- **"Get covariates" family (names lie about source):** `get_model_covariates_from_db` (reads **bbr files**, returns tag **values**), `get_model_covariates_from_files` (reads bbr files, returns tag **names**), `get_covariates_from_models` (DB, many models). **Do not collapse blindly.**
- **Run-success test ×2 (added 2026-07-30 — must stay identical):** `get_model_status_from_files` (file-io.R, returns a status string; used by base-model validation + discovery) and `update_model_status_from_files`'s nested `read_all_model_files` (validation.R, writes the DB row) now apply *the same* rule in the same order: run finished (`.lst` present, not `incomplete`) → usable OFV (non-NA, finite, `abs <= 1e10`, no parameter at `abs >= 8.9999e5`) → `.cov` present when `require_cov_step`. Both resolve output location via `read_nonmem_lst()$file` and look for the `.cov` in `dirname()` of it. Neither has a route to `"completed"` that skips the OFV test: a `.lst` reporting completion with a missing or unparseable `.ext` is `failed` in both. **If they drift, a model's verdict depends on which reader looked at it.** `completed_with_issues` was retired from this path and is no longer produced anywhere in the package. The flag itself is threaded `initialize_covariate_search(require_cov_step=)` → `validate_base_model_for_search` + `initialize_search_config` (stored in `search_config`, **before** `discover_existing_models` runs) → read back via `%||% TRUE` by discovery, `update_model_status_from_files` and `run_automated_scm_testing` (which only overwrites it when the caller supplied it). **Extended 2026-07-31:** the agreement now also covers an *unreadable* listing — both readers call `read_error` `failed` (previously `update_model_status_from_files` reported it as `in_progress`, which the monitoring loop waits on forever), and both read listings only through `.read_listing_lines()` (latin1 + `skipNul`), never bare `readLines()`. The two readers still **name the unfinished state differently** — `update_model_status_from_files` writes `"in_progress"`, `get_model_status_from_files`/discovery write `"incomplete"` — and both spellings sit in checkpoints already on disk, so neither can be renamed; any "is this still running?" guard must go through `.is_pending_status()` rather than an inline status vector.

**Acceptance rule ×1 (consolidated 2026-08-07 — no longer a merge target):** "does this model meet the criteria" (status `completed` + per-covariate-df ΔOFV threshold + RSE limit) used to be re-derived independently at every decision site. It now has **one** implementation, `.evaluate_model_criteria()` (scm-evaluation.R), read by `select_best_model`, `.best_acceptable_model`, `get_significant_models_from_step`/`get_step_models`, `evaluate_removal_impacts`, and `create_scm_results_table`'s nested `get_selection_info`; the RSE limit itself resolves only through `.resolve_rse_threshold()` (utilities.R). **The `phase` argument is not cosmetic** — forward and backward store `delta_ofv` with opposite signs *and* compare it in opposite directions, so a backward step judged with the forward default silently reports the wrong models. **And a phase-aware evaluator is not by itself enough: the candidate *pool* handed to it must be phase-consistent too.** A forward pick over a set that includes backward rows misreads every one of them — a removal that badly worsened the fit looks like a large improvement — no matter which `phase` was passed. This bites any search that *begins* with backward elimination, which then has such rows in the database from the start. `.scm_backward_rows(db)` (continue-search.R) is the row-level filter for this, and `run_scm_selective_forward` applies it at **all four** of its candidate pools; the test *"every forward candidate pool in the file carries the phase filter"* greps the source and fails if any pool lacks it, so a newly added fifth pool cannot silently reintroduce the misread. The filter tests `phase` **OR** `action` (via `.is_removal_model`), not `phase` alone: a retry of a backward removal is written `phase="retry"` yet later receives a backward-signed `delta_ofv`, so phase-only let it into every forward pool. Matching on `action` closes that because it is the same predicate validation.R:336 uses to choose the sign. The base row is matched by neither test (`phase="base"`, `action="base_model"`) and so stays in scope on purpose — the redemption-base fallback needs to find `base_model_id` in that same table. See the two-field note under R/continue-search.R for the sign-writer audit. **One remaining exception, and it is deliberate:** `evaluate_removal_impacts` calls the evaluator but **discards its `meets_threshold`**, recomputing `meets_ofv & meets_rse` without the `status == "completed"` term — by design, because eligibility there is the caller's `completed_models` argument, and `submit_and_wait_for_step()` hands back that list wholesale under `auto_submit = FALSE`, so re-gating on DB status would stall the manual workflow. Do not "fix" it back to `meets_threshold`. (`generate_scm_report` was the other exception — no RSE term, `df=1` hardcoded, final model by `which.max(step_number)`. **Rewritten 2026-08-07** to read every verdict from the evaluator and to track the final model through the accepted winners, so the report and the search can no longer disagree.) The companion invariant is the **sign**: `.signed_delta_ofv()` (utilities.R) is the one place the ΔOFV convention is chosen, off the same `.is_removal_model()` predicate, so a stored delta and the rule that reads it stay in agreement — see its `direction` note under R/utilities.R for when a caller may override it.

**Schema declared in 5 places (must all stay in sync / all get `stage`):** canonical `initialize_search_database_core` (19 cols as of 2026-07-30, `created_by_search` added) · self-heal `required_cols` in `validation.R` (13-col subset) · self-heal in `scm-selective-forward.R` · `model-discovery.R` rebuilds the 19-col row by hand · row-builders `add_covariate_to_model`/`remove_covariate_from_model` (`bind_rows`) + `create_retry_model` (**order-sensitive `rbind` on a blanked `db[1,]` template** — hence its `.ensure_provenance_column()` call). A checkpoint predating a new column is only migrated for `created_by_search`, via `.ensure_provenance_column()` in `load_search_state`/`create_retry_model`; the other four sites have no migration path.

**Known limitations of the `lines_modified` guard (audited 2026-08-12, all three accepted as non-blocking):**
- **Orphan-`$THETA` cleanup now errors instead of succeeding.** A model carrying a `beta_<COV>_<PARAM>` `$THETA` line whose `$PK` reference is already gone used to be tidied up by `remove_covariate_from_model` (delete the line, renumber, done). It now hits the guard, since no equation changes. That shape is not produced by the search itself; if it turns up, the `$THETA` line has to be removed by hand.
- **The `stop()` can fire after the child model file exists.** Step 2 runs `bbr::copy_model_from` *before* the control stream is edited in Steps 3-12, so when the guard trips the `run<N>` files are already on disk while the DB row (Step 11) is never appended and the incremented `model_counter` never reaches the caller (the error propagates; the modified `search_state` is discarded). A backward-elimination step that keeps going past the error is therefore working around an orphan `run<N>` on disk that no database row references — clean it up before resuming, rather than assuming the number is free.
- **`model_add_cov` called directly can still mis-write a conditional-TV model.** The `has_tv_line` check lives in `detect_param_transform`, and the `stop()` that turns a missing line-start `TV_<param>` into an error lives in `validate_param_transformations`. The public path (`initialize_covariate_search` → `validate_setup`) always runs the latter first, so a search cannot reach the bad write. A direct call to the exported `model_add_cov` skips it and can still append the covariate to the `PARAM = EXP(MU+ETA)` line. Validate first, or accept that responsibility.

**Rejected designs (considered, implemented, reverted — do not re-propose):**
- **Gating model success on NONMEM's termination verdict** (tried and reverted 2026-08-07). The idea: have `update_model_status_from_files` consume `read_nonmem_lst()$status == "failed"` and mark the model failed, since the listing already classifies `MINIMIZATION TERMINATED` / `FATAL ERROR` and the caller was discarding it. It looks like free rigour. It is not:
  - It contradicts a **deliberate** decision stated at file-io.R:466-469 — *"How minimisation ended is deliberately not part of it: a run that stopped on rounding errors but produced both is a success."* Success is a usable OFV plus a covariance matrix, nothing else.
  - `MINIMIZATION TERMINATED DUE TO ROUNDING ERRORS` matches `hard_failure_patterns` and is **the most common non-`SUCCESSFUL` outcome in covariate work**; such runs normally do produce a usable OFV *and* a `.cov`. Gating on it would have failed most usable covariate models, and the search would have reported "no significant covariates" — a wrong scientific answer, arrived at silently.
  - The gate returned **before the `.ext` was read**, so it also suppressed OFV/RSE recording for those rows: the OFV the run really did produce vanished from the database and from every report.
  - The obvious defence — make the hard-failure test order-aware, so a failure marker only counts when no success marker follows — has its own false negative. It asks "is there a success after the *first* failure", so `TERMINATED → SUCCESSFUL → TERMINATED` reports `completed`. A three-`$EST` sequence (SAEM → IMP → FOCE) is ordinary, so this is not a corner case either.
  - **The real convergence gate already exists and is `require_cov_step`:** a successful covariance step is stronger evidence of identifiability than a termination string, and it is already threaded through init → config → both readers → `.evaluate_model_criteria`'s RSE rule.
  Net: `read_nonmem_lst()$status` stays a *listing* verdict that no caller treats as disqualifying, and both run-success readers keep the OFV+`.cov` test above.

**Sign/direction consistency — the current, settled picture (2026-08-07).** Three mechanisms interlock, and all three now read the same predicate:
1. `.signed_delta_ofv()` is the sole writer of the ΔOFV sign; `.is_removal_model()` is the sole direction lookup; `.scm_backward_rows()` is the sole pool filter, ORing phase with that same lookup.
2. `.is_removal_model()` itself now **falls back to `phase` for rows whose `action` cannot answer**, so the older failure — a database with no `action` column giving a removal the forward sign while `.scm_backward_rows` read it as backward from its phase — is gone. The two readers can no longer disagree on such a row. `action` remains authoritative where present; a phase that contradicts it is left as a fault to report.
3. The residual risk is no longer a *silent* disagreement but a **mis-assembled candidate list**, and both direction-stating callers (`select_best_model`, `evaluate_removal_impacts`) `warning()` on being handed a model of the wrong kind. That is the one seam left, and it is loud.

**`.DEFAULT_RSE_THRESHOLD` (= 50)** is a package-level *constant*, not a function, so it has no row above. It is the one place the default RSE limit lives: `initialize_search_config()` writes it into a new search's config and `.resolve_rse_threshold()` falls back to it, so the value a search is *created* with and the value an older state is *read* with cannot drift apart.

**When to pass `.signed_delta_ofv(direction=)` and when not to — the rule, not just the signature.** `direction` looks like a wart; it is not. `action` is **not** in `update_model_status_from_files()`'s self-heal `required_cols`, so a database can legitimately lack the column. The rule turns on **what the caller ALSO does**, not on whether its rows are of one kind:
- **Writes the sign AND fixes the acceptance test's direction ⇒ state `direction` to match, and warn on the other kind.** Both `evaluate_removal_impacts` (`phase="backward"` ⇒ `direction="backward"`) and `select_best_model` (`phase="forward"` is a literal ⇒ `direction="forward"`) are in this case. Deriving instead lets the sign and the test disagree whenever the lookup cannot answer: a removal row stored as `model − parent` (say `+50`) and then tested with `delta_ofv > threshold` reads as a 50-point *improvement* and gets **selected**.
- **Writes only, never tests ⇒ leave `direction` NULL** and let each row's own action decide. `update_model_status_from_files` is the sole such caller.

Get this backwards and the failure is silent — a stored delta whose sign disagrees with the rule that reads it. Once sign and test agree, the only way left to be wrong is a mis-assembled candidate list, which is why **both** direction-stating callers `warning()` when handed a model of the opposite kind.

With all-scalar covariates every mask is uniformly TRUE/FALSE, which is the old scalar branch selection. **Covariate registry + `NA` contract (each value coerced with `as.numeric(as.character(...))` under `suppressWarnings` — the `as.character` step defends against factor columns whose internal codes silently differ from their displayed values; text becomes `NA`):** the registry is `known_covs <- as.character(covariate_search$COVARIATE)`, populated **only when `covariate_search` has both a `COVARIATE` and a `REFERENCE` column** (otherwise it is empty). (1) **Scalar value** (named-vector / one-row form, or N=1): an `NA` is **dropped silently** and the covariate falls through to its `REFERENCE` (or stays unassigned if it has no numeric `REFERENCE`); a non-`NA` scalar is assigned **whether or not its name is registered**. (2) **Per-row (length-N) column whose name is NOT in `known_covs`** (e.g. a `Scenario` label) is **ignored entirely**, whatever it holds — numeric, text, all-`NA` — and never enters the eval env. Consequence: in the per-row form only registered covariates can reach `$PK`; a per-row value for an unregistered `$PK` variable is silently discarded. (3) **Per-row column whose name IS registered**: **any** `NA` — one row or every row, including a text column that coerced to all-`NA` — **`stop()`s**, naming the covariate and the `NA` row indices. There is **no `REFERENCE` fallback for a per-row value at all**. **Two separate post-hoc warnings (distinct mechanisms):** (a) the **missing-param warning** fires when a structural parameter's variable **does not exist at all** in the eval env (its defining `$PK` line failed, or **no** row took the branch that assigns it). That column is returned as the **raw sampled THETA**, and the warning lists up to 5 skipped `$PK` lines. (b) the **NA-audit warning** runs at the very end, after the structural output is built: it checks every output column except `ID` and those already named in (a) with `anyNA`, and warns listing any that hold `NA`. Its designed cause is a `$PK` variable first assigned inside a branch that only some rows take, with no `ELSE`/default — `do_assign` initialises the other rows to `NA` (e.g. a valid `SEXN=5` with no matching `IF`/`ELSEIF`). That is a `$PK` coverage problem, not a covariate-input one: a per-row registered covariate with `NA` cannot reach it (case 3 `stop()`s upstream). Because the check is a plain `anyNA`, a `NaN` from the math (e.g. `LOG` of a negative) or an `NA` already present in `individual_thetas` would also trip it. The warning is informational only: the `NA`s are returned as-is, not replaced. **`eta=FALSE` (default) evaluates with `ETA(k)=0`** — the typical subject, unchanged behaviour. **`eta=TRUE` adds between-subject variability**: one MVN(0, Ω) draw per row of `individual_thetas` (`mvtnorm::rmvnorm(method="svd")`, Ω = the model's FINAL `.ext` OMEGA via `.read_final_omega_matrix` → `.make_psd`), paired **by row index** with that row's THETA draw, so each row carries THETA uncertainty + BSV + the covariate effect. **`eta=TRUE` fails fast on an out-of-range ETA:** before interpretation it strips `;` comments from the `$PK`/`$PRED` lines, collects every literal `ETA(k)` (regex `\bETA\(\s*\d+\s*\)`, case-insensitive; `\b` stops `THETA(k)` matching) and `stop()`s if the largest `k` > Ω's column count. The scan is textual — it counts `ETA(k)` inside IF branches that would never be taken for this scenario. It exists because the in-interpreter guard in the `ETA` closure is **swallowed**: every `eval_r()` in `do_assign`/the IF checks is wrapped in `tryCatch`, so a `stop()` from there becomes a skipped line + raw-THETA fallback + `warning()`. That closure guard is still there, so a non-literal index (e.g. `ETA(N)`) that the scan cannot see still degrades silently. **`eta=FALSE` has no ETA validation** — `ETA(k)` is `0` for any `k`.
